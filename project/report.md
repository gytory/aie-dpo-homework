## 2. Постановка задачи и контекст


1. **Предметная область и задачи:**
   - Предметная область - семантический поиск. Проблема - поиск быстрых ответов из заданной базы знаний по введенному запросу пользователя и заданному количеству необходимых документов в выборке.
   - потенциальный пользователь - сотрудник техподдержки, которому необходимо быстро отвечать на типовые запросы. 
   - Сценарий использования - запуск сервиса, ввод запроса пользователя и топ документов для выборки. Ответов является список документов, ранжированный в зависимости от близости к запросу.

2. **Формулировку задачи в терминах ML/ИИ:**
   - Построение системы семантического поиска для базы знаний техподдержки, которая по текстовому запросу пользователя находит наиболее релевантные ответы из предварительно размеченной базы.
   - Синтетический корпус документов состоязий из 40 ответов техподдержки. 
   - Топ-K наиболее релевантных документов из базы знаний (K = 5). Для каждого документа возвращаются: ранг, ID документа, текст ответа, оценка близости (score)
   - Есть ограничение по интерпретируемости скоров, так как они выводятся в форме евклидового расстояния.
   - Пользователь должен видеть не только готовый ответ, но и оценку его релевантности

3. **Целевые метрики качества:**
   - MRR. Использовалась как приоритетнрая метрика для оценки позиции релевантности первого выданного документа и его позиции. 
   - Precision и Recall. Использовались для оценки чистоты выдачи и пропуска релевантных документов.
   - MAP. Учитывает все релевантные документы, а не только первый. Это важно для запросов, у которых может быть несколько правильных ответов
   - Latency. Использовалась для оценки скорости индексации.

## 4. Модели и подходы

### 4.1. Эксперименты с моделями эмбеддингов

Сравнивались три модели sentence-transformers и меры сходства для них
По итогу выявлены 3 лучшие связки:

| Модель | Размер | Язык | Лучшая мера | MRR |
|--------|--------|------|-------------|-----|
| **MiniLM** (paraphrase-multilingual-MiniLM-L12-v2) | 470 MB | Мультиязычный | euclidean | **0.7234** |
| E5 (multilingual-e5-small) | 470 MB | Мультиязычный | cosine | 0.7126 |
| USER2 (deepvk/USER2-small) | 34 MB | Русский | cosine | 0.7037 |

### 4.3. Эксперименты с чанкингом
Был проведен эксперимент с размерами чанкинга. 

| Размер чанка | Overlap | MRR |
|--------------|---------|-----|
| без чанков | - | 0.7123 |
| 20 | 5 | 0.7150 |
| **40** | **20** | **0.7234** |
| 60 | 15 | 0.7201 |

### 4.4. Эксперименты с индексацией
Сравнивалась скорость индексации и оценивался смысл использования HNSW

| Индекс | MRR | Latency (ms) |
|--------|-----|--------------|
| Flat (точный поиск) | 0.5912 | 0.08 |
| HNSW (графовый) | 0.5912 | 0.10 |


### 4.5. Эксперименты с Reranker

Оценивался прирост MRR с использованием реранкера и увеличение задержки ответа.

| Конфигурация | MRR | Latency (ms) |
|--------------|-----|--------------|
| Flat (без reranker) | 0.5912 | 0.07 |
| Flat + Reranker | 0.6058 | 459.85 |

## 5. Экспериментальный протокол и результаты

Здесь важно показать, что выбор финальной модели был осмысленным.

1. **Экспериментальный протокол:**
   - Для оценки мер использовались40 документов, 150 тестовых запросов с разметкой, для оценки скорости - 200 дополнительных документов.
   - Метрики, использованные для оценки: MRR, Precision@5, Recall@5, MAP

2. **Сравнение моделей по метрикам:**

MiniLM показывает лучшие результаты по всем ключевым метрикам:

1. MRR (0.7234) наивысший среди всех моделей. Поскольку в обработке запросов техподдержки важен именно первый выданный документ, выбор производился по MRR.

2. Recall (0.5644) значительно выше, чем у E5 (0.4922) и USER2 (0.5217). Модель находит больше релевантных документов в топе.

3. Precision (0.3480) лучшая точность предсказаний.

4. MAP (0.4294) лучшее среднее качество ранжирования.

Также модель значительно лучше различала тематики обращений. 

| Модель | Конфигурация | MRR | Precision | Recall | MAP |
|--------|-------------|-----|-----------|--------|-----|
| **MiniLM** | MiniLM_euclidean | **0.7234** | **0.3480** | **0.5644** | **0.4294** |
| E5 | E5_cosine | 0.7126 | 0.3013 | 0.4922 | 0.3740 |
| USER2 | USER2_cosine | 0.7037 | 0.3200 | 0.5217 | 0.3936 |

3. **Выбор финальной модели:**
   Для семантического поиска для задач техподдержки выбрана итоговая связка:

   - Модель: `paraphrase-multilingual-MiniLM-L12-v2`
   - Мера сходства: `euclidean`
   - Чанкинг: 40/20
   - Индекс: Flat
   - Реранкер: не используется

   Выбор был сформирован последовательно. 
   
   Сначала была выбрана модель и мера сходства путен сравнения с аналогичными. Далее был выбран индекс путем оценки увеличения MRR и Latency. После этого был проведен эксперимент с реранкером.
   
   С промежуточными и итоговыми выводами можно ознакомиться в ноутбуках проекта.

## 6. Архитектура решения и сервис

Опишите, как из модели получился работающий сервис:

1. **Архитектура пайплайна:**
   Работа сервиса разделена на два этапа: инициализация и обработка запроса.
   При запуске сервиса происходит:

   1. Сервис читает csv-файл базы знаний
   2. Текст каждого ответа разбивается на чанки
   3. Все полученные чанки подаются на вход модели эмбеддингов (MiniLM), а векторы сохраняются в памяти.
   4. Все векторы добавляются в faiss индекс с мерой эвклидово пространство.

   Обработка запроса пользователя происходит по сценарию:

   1. Сервис принимает JSON с полем `query` (текст запроса) и опциональным `top_k` (количество результатов, по умолчанию 5).
   2. Текст запроса также переается модели эмбеддингов и преобразуется в вектор.
   3. Вектор запроса передаётся в FAISS индекс, откуда возварщается `top_k` векторов ближайших документов.
   4. Для каждого найденного документа извлекается оригинальный текст ответа. Формируется JSON-ответ из исходного запроса и массива документов с указанием ранга, ID документа, текста ответа и оценки.
   5. Сформированный ответ отправляется клиенту.

2. **API и endpoints:**
   | Эндпоинт | Метод | Описание |
   |----------|-------|----------|
   | `/health` | GET | Проверка состояния сервиса (модель загружена, индекс построен) |
   | `/predict` | POST | Поиск релевантных ответов по запросу |

   Пример тела запроса `/predict`

   ```json
   {
   "query": "забыл пароль что делать",
   "top_k": 5
   }
   ```

   Пример ответа

   ```json
   {
   "query": "забыл пароль что делать",
   "predictions": [
      {
         "rank": 1,
         "doc_id": "doc_6",
         "text": "Здравствуйте! Спасибо, что выбрали нашу платформу. Для восстановления доступа к аккаунту, пожалуйста, перейдите по ссылке 'Забыли пароль' на странице входа...",
         "score": 0.8912
      },
      {
         "rank": 2,
         "doc_id": "doc_4",
         "text": "Приветствуем вас! Спасибо за обращение. Проблемы со входом могут быть связаны с неверным паролем...",
         "score": 0.7654
      }
   ]
   }
   ```

   Коды ошибок

   | HTTP статус | Описание |
   |-------------|----------|
   | `200` | Успешная обработка запроса |
   | `503` | Сервис не инициализирован (модель или индекс не загружены) |
   | `500` | Внутренняя ошибка сервера (ошибка при обработке запроса) |

3. **Технологический стек:**

   | Компонент | Технология | Версия | Назначение |
   |-----------|------------|--------|------------|
   | Веб-фреймворк| FastAPI | 0.100+ | Создание REST API|
   | ASGI сервер| uvicorn | 0.23+ | Запуск FastAPI приложения, обработка асинхронных запросов |
   | Эмбеддинги | sentence-transformers | 2.2+ | Загрузка предобученных моделей и векторизация текста |
   | Индексация | faiss-cpu | 1.7+ | Построение и поиск по векторному индексу|
   | Обработка данных | pandas | 2.0+ | Чтение CSV файлов и работа с DataFrame |
   | Вычисления | numpy | 1.24+ | Математические операции с векторами |
   | Валидация данных | pydantic | 2.0+ | Валидация входящих запросов и исходящих ответов |

## 8. Ограничения и дальнейшая работа

У проекта есть ограничения. 
- Например, можно было бы сделать расширенную базу знаний, более похожую на базу настоящей техподдержки.
- Нет подключения генеративной модели и сборки контекста из ответов. Пользователь получает не выдержку, а список ответов.
- Нет добавления данных внутри сервиса, работа происходит только с заранее готовым csv-файлом.
- Нет гибридного поиска и эксперимента с ним.
